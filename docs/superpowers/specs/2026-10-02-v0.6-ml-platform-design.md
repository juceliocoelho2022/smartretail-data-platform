# SmartRetail Data Platform v0.6 — ML Platform Design

Date: 2026-10-02
Status: Awaiting written-spec review
Branch: `feature/v0.6-ml-platform`

## 1. Objective

The v0.6 release adds a Machine Learning layer to the SmartRetail Data Platform without coupling model training to the transactional ingestion path.

The delivery order is intentionally sequential:

1. build reproducible historical demand data for development and validation;
2. create a product/day demand Gold data product;
3. engineer time-series features;
4. train and compare forecasting models;
5. track experiments and models with MLflow;
6. publish 7-day demand forecasts to PostgreSQL;
7. expose forecasts through the existing Analytics API and React dashboard;
8. detect anomalies from forecast residuals;
9. orchestrate training and scoring with Airflow.

The primary business use case is **daily demand forecasting per product**. Anomaly detection is built second and reuses the forecast pipeline.

## 2. Current platform baseline

v0.5 already provides:

- Java 21 + Spring Boot ingestion API;
- Transactional Outbox + Kafka;
- Spark Structured Streaming;
- Bronze, Silver and Gold layers in MinIO/S3A;
- Apache Iceberg with JDBC Catalog;
- Airflow orchestration and Data Quality checks;
- PostgreSQL analytics serving schema;
- Spring Boot Analytics API;
- React + TypeScript analytics dashboard;
- validated E2E publication from Gold to the dashboard.

The current validated sample contains only a few orders. That is sufficient for pipeline validation but insufficient for meaningful forecasting. v0.6 therefore introduces a deterministic development dataset without changing the production semantics of the ingestion pipeline.

## 3. Architectural principles

The v0.6 design follows these constraints:

- the ingestion API remains independent from ML workloads;
- Bronze and Silver streaming remain continuous and unchanged in responsibility;
- ML consumes curated analytical data, not raw Kafka events;
- training and scoring are separate operational concerns;
- models are never served directly from the frontend;
- predictions are materialized into the analytics serving layer;
- MLflow is responsible for experiment tracking and model registry metadata;
- MinIO stores ML artifacts;
- PostgreSQL stores MLflow metadata and analytical forecast/anomaly read models;
- no deep-learning framework is introduced in v0.6;
- the first release optimizes for reproducibility, explainability, and portfolio-grade engineering rather than maximum predictive accuracy.

## 5. New Gold data product

Forecasting requires product-level daily demand. The existing sales summary/daily products are not sufficient because they focus on business KPIs rather than a product-level time series.

A new Gold data product will be created:

```text
s3a://smartretail-gold/product-demand-daily/
```

Logical grain:

```text
1 row = productId + eventDate
```

Required columns:

- `eventDate`;
- `productId`;
- `unitsSold`;
- `orderCount`;
- `revenue`;
- `averageUnitPrice`;
- `uniqueCustomers`;
- `processedAt`.

The target variable for forecasting is `unitsSold`.

The production form of this data product is derived exclusively from Silver and is reconstructible.

## 6. Historical data generation

Because the current local sample is too small for ML, v0.6 will include a deterministic synthetic-history generator used only for development, testing, demos, and model evaluation.

The generator will create **Silver-compatible synthetic order rows**, not precomputed forecast features or pre-aggregated predictions. The generated rows will include the fields required by the product-demand Gold builder, including event/date, customer, product, quantity, unit price, channel, location, and revenue values.

The generator will produce:

- 365 days of history;
- 30 products;
- multiple order rows per product/day where demand is nonzero;
- product-specific base demand;
- weekly seasonality;
- gradual trend;
- deterministic pseudo-random noise from a fixed seed;
- occasional controlled demand spikes used later to validate anomaly detection.

The generated dataset will be reproducible from the same seed and will never be presented as real retail data.

To avoid polluting the operational Silver dataset, the generator writes to a dedicated development source:

```text
s3a://smartretail-silver/orders-ml-history/
```

The product-demand Gold builder accepts a configurable Silver source path. Its production default remains:

```text
s3a://smartretail-silver/orders/
```

The local ML demo/training flow points that same builder to `orders-ml-history`. This preserves the rule that `product-demand-daily` is built from a Silver-compatible curated source while keeping synthetic development data isolated from the transactional pipeline.

## 7. Feature engineering

Feature engineering will be implemented with PySpark.

For each `productId` and `eventDate`, the model dataset will contain:

- `unitsSold` target;
- lag 1 day;
- lag 7 days;
- lag 14 days;
- rolling mean 7 days;
- rolling mean 28 days;
- rolling standard deviation 7 days;
- day of week;
- day of month;
- month;
- weekend flag;
- sequential time index.

Rows without enough history for required lag/rolling features will be excluded from model training.

No future-derived feature may be used for a historical prediction row.

## 8. Training, validation, and test strategy

Time-series data will never be randomly shuffled for the train/test split.

The chronological split is:

- training: all eligible rows before the final 56 days;
- validation: days `-56` through `-29`;
- test: final 28 days.

The validation set is used for model comparison and parameter selection. The test set is used once for final evaluation of the selected learned model configuration.

Primary metric:

- MAE — Mean Absolute Error.

Secondary metrics:

- RMSE — Root Mean Squared Error;
- WAPE — Weighted Absolute Percentage Error.

MAPE is not a required acceptance metric because retail demand may contain zero-demand days.

## 9. Forecast models

The first release compares three approaches.

### 9.1 Seasonal naive baseline

Prediction:

```text
forecast(t) = unitsSold(t - 7 days)
```

The seasonal naive result is an evaluation benchmark. It is tracked in MLflow but is not registered as the serving model.

### 9.2 Random Forest regression

Implemented with Spark MLlib `RandomForestRegressor`.

Purpose:

- nonlinear baseline;
- robust portfolio implementation;
- simple feature-importance inspection;
- no external model-serving dependency.

### 9.3 Gradient-Boosted Trees regression

Implemented with Spark MLlib `GBTRegressor`.

Purpose:

- stronger nonlinear candidate;
- direct comparison against Random Forest and seasonal naive.

The learned candidate with the lowest validation MAE is eligible for promotion only when:

- MAE, RMSE, and WAPE are finite;
- forecast sanity checks pass;
- validation MAE is strictly lower than the seasonal naive validation MAE.

If neither learned model beats the baseline, no new model is promoted and the previous champion remains active. On the first-ever training run, absence of an eligible model is a training failure. The deterministic synthetic dataset used for the E2E acceptance test must therefore demonstrate at least one learned model beating the baseline.

## 10. MLflow design

A dedicated MLflow Tracking Server will run in Docker Compose.

Metadata backend:

```text
PostgreSQL database: smartretail_mlflow
```

The database runs on the existing PostgreSQL service but is logically separate from the transactional/analytics database.

Artifact storage:

```text
MinIO
bucket: smartretail-mlflow
```

Tracked information per run:

- model type;
- feature set version;
- training date range;
- validation date range;
- test date range;
- model parameters;
- baseline MAE;
- MAE;
- RMSE;
- WAPE;
- row counts;
- model artifact;
- feature metadata;
- training summary.

Registered model name:

```text
smartretail-demand-forecast
```

The promoted production candidate receives the MLflow model alias:

```text
champion
```

The scoring pipeline loads the model registered with this alias rather than referencing an experiment run directly.

## 11. Forecast scoring

The scoring job produces a 7-day forecast horizon for every known product.

Output grain:

```text
productId + forecastDate
```

Each prediction contains:

- `productId`;
- `forecastDate`;
- `predictedUnits`;
- `modelName`;
- `modelVersion`;
- `generatedAt`;
- `trainingCutoffDate`.

Predicted demand is clamped to a minimum of zero before publication because negative unit demand is not meaningful.

## 12. PostgreSQL serving schema

Two new read-model tables will be added under the existing `analytics` schema.

### 12.1 `analytics.demand_forecast`

Logical key:

```text
product_id + forecast_date + model_version
```

Columns:

- `product_id`;
- `forecast_date`;
- `predicted_units`;
- `model_name`;
- `model_version`;
- `training_cutoff_date`;
- `generated_at`.

### 12.2 `analytics.sales_anomaly`

Columns:

- `event_date`;
- `product_id`;
- `actual_units`;
- `expected_units`;
- `residual`;
- `anomaly_score`;
- `is_anomaly`;
- `model_version`;
- `detected_at`.

These are analytical read models and are not written by the ingestion API.

## 13. Anomaly detection

Anomaly detection is based on forecast residuals instead of introducing a separate unrelated ML model.

For a product/day with an available prediction:

```text
residual = actualUnits - expectedUnits
```

A robust residual score is calculated per product using historical residual dispersion. Median Absolute Deviation (MAD) is used instead of plain standard deviation so isolated spikes have less influence on the threshold.

The robust scale is:

```text
robustScale = max(1.4826 * MAD, 0.000001)
anomalyScore = abs(residual - medianResidual) / robustScale
```

A row is classified as anomalous when `anomalyScore >= 3.5`.

The anomaly pipeline keeps the raw residual and score, not only the boolean classification.

## 14. Airflow orchestration

Training and scoring use separate DAGs because model training should not run on every analytics refresh.

### 14.1 Training DAG

DAG name:

```text
smartretail_ml_training
```

Flow:

```text
validate_ml_source
        ↓
build_product_demand_gold
        ↓
build_ml_features
        ↓
train_forecast_models
        ↓
evaluate_and_register
        ↓
validate_registered_champion
```

Default execution mode is manual for the portfolio environment. A weekly schedule may be enabled through configuration without changing DAG logic.

### 14.2 Scoring DAG

DAG name:

```text
smartretail_ml_scoring
```

Flow:

```text
validate_champion_model
        ↓
generate_demand_forecast
        ↓
publish_demand_forecast
        ↓
detect_sales_anomalies
        ↓
publish_sales_anomalies
        ↓
validate_ml_serving
```

Default execution mode is manual for local validation. A daily schedule may be enabled through configuration without changing DAG logic.

The existing `smartretail_lakehouse_pipeline` remains responsible for Data Quality, Gold, Iceberg, and analytics serving. v0.6 does not make normal analytics publication depend on successful model training.

## 15. Analytics API extensions

The existing Analytics API will gain read-only endpoints.

### Demand forecast

```http
GET /api/v1/analytics/forecast/demand
```

Optional filters:

- `productId`;
- `from`;
- `to`;
- `limit`.

### Anomalies

```http
GET /api/v1/analytics/anomalies
```

Optional filters:

- `productId`;
- `from`;
- `to`;
- `onlyAnomalies`;
- `limit`.

The API reads PostgreSQL serving tables only. It does not load MLflow models and does not execute inference inside HTTP requests.

## 16. Dashboard extensions

The React Analytics Dashboard will add two bounded views.

### 16.1 Demand Forecast

Displays:

- selected product;
- historical daily units;
- 7-day predicted units;
- model version;
- forecast generation timestamp.

The first implementation uses a simple time-series visualization and table; no advanced BI framework is required.

### 16.2 Anomalies

Displays:

- product;
- date;
- actual units;
- expected units;
- residual;
- anomaly score;
- anomaly status.

Anomalous rows must be visually distinguishable from normal rows.

## 17. Error handling and operational behavior

### Data validation failures

Training stops when:

- source dataset is empty;
- required columns are missing;
- fewer than 120 distinct historical dates are available;
- feature engineering produces no eligible rows;
- target contains invalid negative values.

### Training failures

No model is promoted when:

- metrics are non-finite;
- learned candidates do not beat the seasonal naive baseline;
- model artifact cannot be persisted;
- MLflow registration fails;
- champion validation fails.

The previous champion remains available when one exists.

### Scoring failures

Forecast publication is not performed when:

- no champion alias exists;
- the model artifact cannot be loaded;
- feature schema is incompatible;
- generated output is empty;
- predictions contain non-finite values.

### Serving publication

Forecast/anomaly writes must not destroy the previously valid read model before the replacement dataset is ready. The implementation plan must use staging plus transactional merge/swap, or an equivalent atomic publication strategy, rather than a truncate-then-multi-write sequence.

## 18. Testing strategy

### Unit tests

PySpark tests will cover:

- product/day aggregation;
- deterministic synthetic generation;
- lag features;
- rolling features;
- no future-data leakage;
- chronological split;
- metric calculations;
- baseline comparison;
- negative forecast clamping;
- residual computation;
- MAD zero-protection;
- anomaly threshold behavior.

Java tests will cover:

- forecast repository queries;
- anomaly repository queries;
- filter normalization;
- invalid date ranges;
- controller response contracts.

Frontend CI will continue to require a successful TypeScript/Vite build.

### Integration tests

The local E2E validation must prove:

1. deterministic Silver-compatible historical data is generated;
2. product-demand Gold exists;
3. features are built;
4. MLflow receives baseline and learned-model runs with metrics;
5. an eligible champion model is registered;
6. scoring generates 7 future dates per product;
7. forecasts are written to PostgreSQL atomically;
8. anomaly rows are written to PostgreSQL atomically;
9. Analytics API returns forecasts/anomalies;
10. React dashboard renders both views;
11. Airflow training DAG ends in `success`;
12. Airflow scoring DAG ends in `success`.

## 19. CI strategy

A dedicated ML workflow will be introduced:

```text
.github/workflows/ml-ci.yml
```

It will validate:

- Python formatting/static checks adopted by the implementation;
- PySpark ML unit tests;
- importability of training/scoring modules;
- Airflow DAG parsing;
- Docker Compose configuration for MLflow and ML jobs.

Existing backend, streaming, analytics, and dashboard workflows remain independent.

## 21. Non-goals for v0.6

The following are explicitly outside this release:

- real external retail datasets;
- online feature store;
- real-time model serving endpoint;
- GPU training;
- deep learning;
- LLM integration;
- automated hyperparameter optimization service;
- Kubernetes deployment;
- multi-tenant model registry;
- automatic business actions such as stock purchasing;
- retraining triggered on every order event.

## 22. Acceptance criteria

v0.6 is complete only when all of the following are demonstrated:

- deterministic 365-day synthetic Silver-compatible history is reproducible;
- `product-demand-daily` is generated through the same builder used for curated Silver data;
- feature pipeline is tested for time leakage;
- seasonal naive, Random Forest, and GBT are evaluated;
- MAE, RMSE, WAPE, and baseline MAE are tracked in MLflow;
- at least one learned model beats the seasonal naive baseline on the deterministic acceptance dataset;
- a valid champion model is registered;
- a 7-day product-level forecast is generated;
- forecasts are persisted in `analytics.demand_forecast`;
- residual-based anomalies are persisted in `analytics.sales_anomaly`;
- Analytics API exposes forecast and anomaly read models;
- React dashboard displays forecast and anomaly views;
- ML training and scoring DAGs complete successfully;
- ML CI passes on the feature branch and after merge to `main`;
- README and roadmap describe v0.6 as implemented only after E2E validation.

## 23. Delivery sequence

Implementation will be planned in this order:

```text
v0.6.1 Historical Silver-compatible dataset + product-demand Gold
v0.6.2 Feature engineering
v0.6.3 MLflow infrastructure + experiment tracking
v0.6.4 Baseline/RF/GBT training + champion registration
v0.6.5 Forecast scoring + atomic publication
v0.6.6 Forecast API + dashboard
v0.6.7 Residual anomaly detection + API/dashboard
v0.6.8 Airflow E2E + CI + documentation
```

This sequence ensures the forecasting foundation is stable before anomaly detection is added.
