# SmartRetail v0.6 ML Platform Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a reproducible ML layer that trains and registers a product-level daily demand forecast model, publishes 7-day forecasts and residual-based anomalies, and exposes them through the existing Analytics API and React dashboard.

**Architecture:** ML consumes curated Silver-compatible data, builds a product/day Gold data product and leakage-safe time-series features, tracks candidates in MLflow, promotes an eligible learned model, then scores and stages serving data before transactional PostgreSQL publication. Training and scoring are independent Airflow DAGs; the existing ingestion/streaming/lakehouse/analytics path remains operational without ML.

**Tech Stack:** Apache Spark 4.0.1 / PySpark MLlib, MLflow 3.16.1, MinIO/S3A, PostgreSQL 17, Apache Airflow 3.3.2 + DockerOperator, Java 21 + Spring Boot 3.5.5 + Spring JDBC + Flyway, React 19 + TypeScript + Vite, Docker Compose, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-02-v0.6-ml-platform-design.md`

## Global Constraints

- Primary use case: daily demand forecasting per `productId`; anomaly detection comes second and reuses forecast residuals.
- Synthetic development history is deterministic, spans 365 days and 30 products, and is explicitly demo/test data.
- Local ML history is isolated at `s3a://smartretail-silver/orders-ml-history/`; production `product-demand-daily` uses the normal Silver path through the same builder.
- Forecast target is `unitsSold`; future horizon is exactly 7 days.
- Split is chronological: train before final 56 days, validation days `-56` through `-29`, test final 28 days.
- Metrics: MAE primary; RMSE and WAPE secondary; MAPE is not an acceptance metric.
- Candidates: seasonal naive, Spark MLlib `RandomForestRegressor`, Spark MLlib `GBTRegressor`.
- A learned model is eligible only when MAE/RMSE/WAPE are finite, sanity checks pass, and validation MAE is strictly below seasonal naive validation MAE.
- If no learned candidate qualifies, preserve an existing champion; on the first training run, no eligible champion is a failure.
- Registered model: `smartretail-demand-forecast`; serving alias: `champion`.
- Scoring loads `models:/smartretail-demand-forecast@champion`.
- Forecasts are clamped to zero minimum before serving publication.
- Anomaly formula: `robustScale = max(1.4826 * MAD, 0.000001)` and `anomalyScore = abs(residual - medianResidual) / robustScale`; anomalous when `>= 3.5`.
- MLflow backend database: `smartretail_mlflow`; artifacts bucket: `smartretail-mlflow`.
- Serving publication is staging-first and live-table replacement is one PostgreSQL transaction; never truncate a valid live table before staging succeeds.
- Existing ingestion, Bronze/Silver streaming, lakehouse DAG, analytics export, Analytics API, and dashboard overview must remain backward compatible.
- No deep learning, GPU, LLM, online feature store, real-time inference endpoint, Kubernetes, automated HPO service, or per-event retraining in v0.6.
- Dependency pin for this plan: `ghcr.io/mlflow/mlflow:v3.16.1-full` and Python `mlflow==3.16.1`.

## Review Focus

- Missing product/date combinations: Task 2 tests continuous product calendars and zero-filled demand measures.
- Time leakage: Task 3 tests lags/rolling windows against a known sequence and excludes the current target from rolling features.
- Baseline not beaten: Task 5 tests preservation of an existing champion and first-run failure with no eligible model.
- Missing champion/non-finite forecast: Task 6 tests failure before any staging/live mutation.
- Failure after staging: Task 6 tests rollback/commit semantics and proves the live table is not touched when staging fails.
