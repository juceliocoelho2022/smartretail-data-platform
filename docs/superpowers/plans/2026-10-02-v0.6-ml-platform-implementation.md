# SmartRetail v0.6 ML Platform Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a reproducible ML layer that trains and registers a product-level daily demand forecast model, publishes 7-day forecasts and residual-based anomalies, and exposes them through the existing Analytics API and React dashboard.

**Architecture:** ML consumes a curated Silver-compatible source and builds `product-demand-daily`, time-series features, MLflow-tracked models, forecasts, and anomalies without coupling training to the ingestion path. Training and scoring are separate Airflow DAGs; PostgreSQL remains the serving layer for API/dashboard reads, while MinIO stores data and MLflow artifacts.

**Tech Stack:** Apache Spark 4.0.1 / PySpark MLlib, MLflow 3.16.1, MinIO/S3A, PostgreSQL 17, Apache Airflow 3.3.2 + DockerOperator, Java 21 + Spring Boot 3.5.5 + Spring JDBC + Flyway, React 19 + TypeScript + Vite, Docker Compose, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-02-v0.6-ml-platform-design.md`

## Global Constraints

- Primary use case: daily demand forecasting per `productId`; anomaly detection is second and reuses forecast residuals.
- Synthetic development history is deterministic, spans 365 days and 30 products, and is never represented as real retail data.
- Production `product-demand-daily` is derived from curated Silver; local ML validation uses isolated `s3a://smartretail-silver/orders-ml-history/` through the same builder.
- Forecast target is `unitsSold`; forecast horizon is exactly 7 days.
- Time-series splits are chronological: training before the final 56 days, validation days `-56` through `-29`, test final 28 days.
- Primary metric is MAE; secondary metrics are RMSE and WAPE. MAPE is not an acceptance metric.
- Candidates are seasonal naive, Spark MLlib `RandomForestRegressor`, and `GBTRegressor`.
- A learned model may receive MLflow alias `champion` only if metrics are finite, sanity checks pass, and validation MAE is strictly lower than seasonal naive validation MAE.
- If no learned candidate beats baseline, preserve the previous champion; on the first-ever run, absence of an eligible champion is a training failure.
- Registered model name is `smartretail-demand-forecast`; scoring loads `models:/smartretail-demand-forecast@champion`.
- Forecasts are clamped to zero minimum before publication.
- Anomaly score uses `robustScale = max(1.4826 * MAD, 0.000001)` and `abs(residual - medianResidual) / robustScale`; anomaly threshold is `>= 3.5`.
- MLflow backend database is `smartretail_mlflow`; artifact bucket is `smartretail-mlflow`.
- Forecast/anomaly publication must stage data first and replace the live read model transactionally; never truncate the valid live table before staging succeeds.
- Ingestion, Bronze, Silver, existing lakehouse DAG, analytics publication, and existing APIs must continue working independently of ML training.
- No deep learning, GPU, LLM, online feature store, real-time model serving, Kubernetes, automated HPO service, or retraining per event in v0.6.
- Implementation pin: use `ghcr.io/mlflow/mlflow:v3.16.1-full` for the tracking server and `mlflow==3.16.1` in ML jobs.

## Review Focus

- Missing product/date combinations: `product-demand-daily` must produce a continuous daily calendar per product and zero-fill `unitsSold`, `orderCount`, and `revenue`; Task 2 tests this explicitly.
- Time leakage: lag/rolling features must use only prior dates, never the current/future target; Task 3 has a known-sequence leakage test.
- Baseline not beaten: training must not overwrite an existing `champion`, and first-run training must fail cleanly; Task 5 tests both behaviors.
- Missing/invalid champion or non-finite scoring output: scoring must fail before live-table publication; Task 6 tests these guards.
- Failure after staging: live serving rows must remain untouched when staging write or transactional swap fails; Task 6 tests commit/rollback behavior with a mocked PostgreSQL connection and the final E2E validates it against real PostgreSQL.
